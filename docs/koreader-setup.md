# KOReader 装到用起来 · 一步步的手册（含对账）

这份文档是给你（拿到设备的人）看的：从零开始装插件、报一次时长、把它交上去，
最后**自己验一遍数字对不对**。

插件自己的说明书在 [`plugin/koreader-dex.koplugin/README.md`](../plugin/koreader-dex.koplugin/README.md)，
项目总览在 [仓库根 README](../README.md)。

---

## 这套东西是三段接力

```
Kindle / 平板上的 KOReader
  └─ 插件读自己的统计库 → 屏幕上弹一个二维码（链接里带着「哪天读了多久」）
       └─ 手机扫码 → 打开落地页（手机浏览器里显示分钟数和折算出的额度）
            └─ 落地页给一个「去 GitHub 提交」按钮 → 打开预填好的新建 issue 页
                 └─ 你点一下 Submit → 服务端的定时任务读这条 issue
                      └─ 并进逐日账本 → 当天额度够了就掉一只宝可梦
```

三段的分工要记牢：

- **设备上的插件只报数**，不上传、不抽卡。
- **落地页只算数**，它不发任何写请求（纯静态页收不了 POST）。
- **只有服务端能记账和掉宝可梦**。

---

## 你要准备什么

- 一台装了 KOReader 的设备（Kindle / Kobo / Android 都行）。
- 一部能上网的手机（扫码 + 提交 issue 用）。
- 一个 **GitHub 账号**，而且它得是 `lilia-shound/pokemon-dex` 这个仓库的**管理员或协作者**
  —— 服务端只认这些身份的 issue（`author_association` 在 `OWNER` / `MEMBER` / `COLLABORATOR` 里）。
  别人（或匿名）提的 issue 会被跳过，而且**不会被关掉**，留给人工看。
- 仓库的 issue 功能是开着的（默认就开着）。

## 第一步：装插件

1. **先拿到插件文件**（三选一，都行）：

   | 方式 | 地址 |
   |---|---|
   | **线上目录（发布之后才有）** | <https://lilia-shound.github.io/pokemon-dex/koreader-dex.koplugin/> |
   | 仓库目录 | <https://github.com/lilia-shound/pokemon-dex/tree/main/plugin/koreader-dex.koplugin> |
   | 已有源码的机器 | 仓库里的 `plugin/koreader-dex.koplugin/` |

   ⚠️ **线上那个地址要等 `scripts/deploy.sh` 跑完（发布）之后才会有** ——
   现在还没部署，点过去是 404；插件改过之后也要重新发布一次才会更新。
   「仓库目录」和「已有源码的机器」这两条**现在就能用**，不依赖部署。

   线上那个地址是**整个插件目录**（`main.lua`、`koreader_dex_report.lua`、`_meta.lua`、`README.md`），
   一个个文件下下来，放进一个叫 `koreader-dex.koplugin` 的文件夹里即可
   （**目录名不能改**，KOReader 靠它认出插件）。

   **文件直链**（一个一个下，不想用目录页就点这四条）：

   - `main.lua`：<https://lilia-shound.github.io/pokemon-dex/koreader-dex.koplugin/main.lua>
   - `koreader_dex_report.lua`：<https://lilia-shound.github.io/pokemon-dex/koreader-dex.koplugin/koreader_dex_report.lua>
   - `_meta.lua`：<https://lilia-shound.github.io/pokemon-dex/koreader-dex.koplugin/_meta.lua>
   - `README.md`：<https://lilia-shound.github.io/pokemon-dex/koreader-dex.koplugin/README.md>

   > 目录页（`…/koreader-dex.koplugin/`）**只是索引**：打开后能看到目录里有哪几个文件，
   > **文件直链就在那一页的最下面**（也就是上面这四条）。

2. 把 `koreader-dex.koplugin/` 这个目录复制到设备的 **`plugins/` 目录**里。
   - Kindle 上一般是把挂载出来的 `koreader/plugins/` 目录（常见是 `/mnt/us/koreader/plugins/`）拷进去。
   - 固件路径不一样的话，以「设备上的 koreader/plugins/ 目录」为准。
   - **注意别多套一层**：设备上应该是 `plugins/koreader-dex.koplugin/main.lua`，
     而不是 `plugins/koreader-dex.koplugin/koreader-dex.koplugin/main.lua`。
3. **退出 KOReader 再打开**（关掉书不算重启）。
4. 打开主菜单（☰），按这个路径找：
   「**工具**」→「**更多工具**」→「**训练家图鉴**」，点开应该能看到三项：
   `汇报阅读时长（最近 7 天）`、`只汇报今天`、`自检`。

   > 位置说明：插件用 `sorting_hint = "more_tools"` ⇒ 它在**工具 → 更多工具**里；
   > 内置那个「阅读统计（Reading statistics）」在**工具**一级（不是「更多工具」）—— 别认错。
   > 不同 KOReader 版本 / 语言的分组文案会有差别，实在找不到就翻到主菜单底部。

找不到这一项，先看 `plugin/koreader-dex.koplugin/README.md` 的「菜单里有什么」。

## 第二步：让 KOReader 先把统计库建起来

插件读的是 KOReader **内置 statistics 插件**自己记的库（`statistics.sqlite3`）。
正常情况下 KOReader 一启动，内置插件就会把这个库建好、必要时还会升级 schema
（它是在插件初始化的时候干的）—— 所以装完插件、重启一次，库通常就已经在了。

万一插件提示「KOReader 的统计数据库还没建」或者「让它把数据库升级」，那就：

- 读一会儿书（几页就够），**然后关掉那本书**；或者
- 在 KOReader 里打开一次「**工具 → 阅读统计（Reading statistics）→ 时长范围（Time range）**」
  （它会顺手把库建好/升级好）。

**建议顺手检查内置统计是开着的**：在「**工具 → 阅读统计（Reading statistics）**」那一项里，
开关是它的**第一个子项**「**已启用（Enabled）**」。
⚠️ **它不在「设置」页里** —— 上游把它挂在「工具」组，设置页里翻不到是正常的。
关着的话，插件会直接告诉你「内置的 Reading statistics 没打开」，读了也是旧数据。

## 第三步：报一次时长

在 KOReader 主菜单 →「工具」→「更多工具」→「训练家图鉴」→ 挑一项：

- `汇报阅读时长（最近 7 天）` —— 一次把最近 7 天有记录的日子都带上（推荐第一次用这个）。
- `只汇报今天` —— 只报今天。

屏幕上先弹一段字（`今天 25 分钟 → 折算 1 个额度` 这种），关掉它就弹二维码。

> ⚠️ **刚读完的几页可能还没进库。** 内置 statistics 是攒着写库的（每 50 次翻页 / 关掉书 / 息屏才落库）。
> 看到插件提示「关掉书或息屏后再汇报」，就照做：**关掉那本书**（或让屏幕息屏），
> 然后再点一次汇报，数字才全。

## 第四步：手机那边（Kindle → 手机）

用手机相机扫 Kindle 屏幕上那个二维码 → 浏览器打开落地页。

落地页上你该看到：

- 标题「KOReader 阅读时长」，下面一行「交回训练家图鉴 · 只报数，不抽卡」。
- 「读到的时长」那张卡：**每一天一行**（日期 / 分钟 / 个额度），下面一行「合计 X 分钟」，
  再下面一个大数字「折算成 **N** 个额度」。
- 底下有一行小字：`15 分钟 = 1 个额度（按天算，零头不计）`。
- 一个按钮「**去 GitHub 提交**」（点开是新标签页）。

如果页面显示的是「😅 没读出有效的时长」，那是**链接不完整**（短链被截断了）——
回设备上重新弹一次二维码再扫。

### 如果你在同一台手机上用 KOReader（Android 版）

同一个屏幕没法用相机扫自己 ⇒ 这条路走不通。插件这时候会**把链接复制到剪贴板**，
你就：

1. 在 KOReader 里点汇报，屏幕弹出那段字；
2. 关掉 KOReader（或直接切到浏览器）；
3. 长按浏览器的地址栏 →「粘贴」→ 回车。

插件提示「同一条链接已经复制到剪贴板了（二维码扫不出来时可以手动粘贴）」就说明复制成了。
**没有这一行提示** = 这台设备上复制失败了，那就只能换台设备扫（或者用别的办法把这串字符复制出来）。

## 第五步：交上去

落地页上点「**去 GitHub 提交**」→ 打开 GitHub 的新建 issue 页，标题和内容**都已经填好了**：

- 标题：`[report] koreader 2026-11-21`（后面那串是最新的一天）
- 内容：一段 JSON，形如 `{"v":1,"source":"koreader","days":{"2026-11-21":25,"2026-11-20":50}}`

**在那个页面上点一下 `Submit` 才算交上去**（按钮在页面下方，GitHub 把它放在正文框下面那排）。
别改标题和内容（改了服务端会当成非法报告丢掉）。

交完之后：

- 服务端的定时任务会在**下一个结算周期**去读这条 issue（不是立刻，通常几小时到一天）。
- 读到了就并进账本、在 issue 下留一条评论、然后把 issue 关掉。
- **重复提交不会重复计数**：同一源同一天是取最大值，所以多点几次 `Submit` 是安全的。

## 额度是怎么算的

- **15 分钟 = 1 个额度**（KOReader 这个源的口径，在 `data/sources.json` 里写着 `per: 15`）。
- **按天算、零头不计**：一天读了 20 分钟 = 1 个额度（不是 1.33 个）；
  **不跨天凑零头**。
- **每天满 2 个额度才掉 1 只宝可梦**（`perAward = 2`）⇒ **KOReader 单独读满 30 分钟（同一天）= 1 只**。
- **一天最多 1 只**，额度**跨天清零**。
  ⚠️ 所以「周一 15 分钟 + 周二 15 分钟」= 每天各 1 个额度，**掉不了宝可梦** ——
  30 分钟得**在同一天**读完。
- **微信读书和 KOReader 是两个独立的源**，不是同一个东西的两份统计：
  各自按天取整算出自己的额度，然后**相加**。
  - 微信读书：900 秒 = 1 个额度
  - 番茄钟：25 分钟 = 1 个额度
  - KOReader：15 分钟 = 1 个额度

  所以「微信读书读 15 分钟（1 额度）+ KOReader 读 15 分钟（1 额度）」= 当天 2 个额度 = 掉 1 只。
  反过来，KOReader 单独报了「折算 1 个额度」也别急着难过 —— 那只是这一个源的额度，
  微信读书那份可能已经凑上另一个了。
- 服务端结算时也会**补发**：某天后来才凑满 2 个额度、但那天还没发过奖，结算任务会回头补上
  （最多补 3 天）。

## 四步对账：数字对不对，自己验一遍

这是验收这一整套东西的**唯一手段** —— 我们手边没有真机，代码在沙箱里测过，
但「设备上的数字和手机上的数字、服务端算出来的数字是不是同一份」只能靠你在真机上对一遍。

**从第 1 步开始，任何一步对不上就停下来**，先弄明白是哪一环错了，再决定要不要提交。
（先提交再发现错，账已经进了一半，得手动收拾。）

### 第 1 步 · 设备上：自检表 ↔ KOReader 自带的统计

**你做什么**

1. KOReader 主菜单 →「**工具**」→「**阅读统计（Reading statistics）**」→「**时长范围（Time range）**」
   （页面标题是「**时长范围统计（Time range statistics）**」）→ 点「**最近一周（Last week）**」
   （最近 7 天，逐天）和「**最近一个月按天统计（Last month by day）**」（最近 30 天，逐天）。
   > 同一页里还有「**最近一年按天统计（Last year by day）**」（365 天）—— **我们用不上**：
   > 插件的自检表只到 30 天，对账只用上面那两张。
2. 记住这两页每行的样子：`2026-11-19 (周四)   00:45:30 (3 pages)`
   （括号里的星期几是本机语言：中文界面是「周四」，英文界面是「Thu」；时长是 时:分:秒）。
3. 回到主菜单 →「工具」→「更多工具」→「训练家图鉴」→「**自检**」→ 记下那张 30 天的表。

> ⚠️ **顺序不能反：先打开内置那一页（第 1 步），再跑插件自检（第 3 步）。**
> 内置 statistics 在**查询之前**会先把当前统计写进库（上游 `getDatesFromAll` 里先 `insertDB()`）——
> 所以**先开内置那一页**，它落库之后两边读到的是**同一批**数据。
> 反过来（先跑自检、再开内置那一页），内置那边会**多出刚落库的那一段** ⇒
> 两边对不上 ⇒ **那是假警报，不是插件坏了**。对不上时，先按这个顺序重来一遍。

**看到什么算对**

- 自检表里**同一个日期**那一行：分钟数和页数**必须和内置那边一样**。
- 分钟的换算：内置显示 时:分:秒，插件显示**整分钟、丢掉秒数**。
  - 内置 `00:45:30` ⇒ 插件 `45 分钟` ✅
  - 内置 `00:00:45` ⇒ 插件 `0 分钟` ✅（这类天插件照样列出来，只是 0 分钟 —— 是故意的，
    为了让你能一天一天对上号）
  - 所以**差在 1 分钟以内是正常的**（那是秒数被丢掉了），差很多就不正常。
- 页数要**一模一样**，一个都不能差。
- 内置那几行**多一个括号里的星期几**（`(周四)`）—— 插件那张表没有这一列 ⇒ **只对日期和数字**。
- 「Last week」是最近 7 天、「Last month by day」是最近 30 天；插件的自检表也是 30 天 ——
  两边都只列**有记录的天**，所以不会出现「内置有、插件没有」的日子；
  如果出现了（插件这边少一天），多半是刚读的那几页还没落库，或者你是在跨过零点的那天对账的。

**对不上怎么办**

- 差几分钟 ⇒ 多半是秒数被取整了，正常。
- **多出刚读的那一段 / 少一天** ⇒ 先检查顺序对不对（见上面那个 ⚠️），
  再检查是不是刚读的那几页还没落库。
- **时长的写法看不懂**（比如 `1h30'` 而不是 `00:45:30`）⇒ 内置的**时长显示格式**跟着设置走：
  默认是 classic（时:分:秒），改过设置就可能是 `1h30'`（modern）或 `1h 30m 30s`（letters）——
  **把它改回 classic 再对账**（KOReader 设置里的时长格式选项）。
- 差很多天 / 页数差很多 ⇒ **停下来**，八成是两边读的不是同一个库（比如内置统计刚被重置过），
  这时候把自检表第一行「数据来源：」后面那个路径记下来，去看那个文件是不是你 KOReader 现在在用的。
- 设备时区不是 UTC+8 的话，跨过午夜零点的那几页会被归到不同的一天 ——
  内置和插件**都会**这么归（两边用的同一条 SQL），所以还是会对上；只是那一天的日期可能不是你以为的那天。

### 第 2 步 · 手机上：落地页 ↔ 设备上的数字

**你做什么**：在设备上点「汇报阅读时长（最近 7 天）」→ 手机扫二维码 → 看落地页。

**看到什么算对**

- 落地页上**每一天的分钟数** = 设备上自检表里**同一天那一行**的分钟数（一模一样）。
- 落地页的「合计 X 分钟」= 设备上弹的那段字里的「共 X 分钟」。
- 落地页的大数字「折算成 N 个额度」= 设备上弹的那段字里的「折算 N 个额度」。
- 天数可能不一样：落地页只列**有记录（分钟数 > 0）**的天，自检表会连 0 分钟的天一起列。
  ⇒ **只看落地页上有的那些天**，它们必须能在自检表里找到对应的行。

**对不上怎么办**

- 落地页显示「😅 没读出有效的时长」⇒ 链接不完整，**回设备上重新弹一次二维码**再扫。
- 数字差一点点（1~2 分钟）⇒ 正常：插件报的是「弹二维码那一刻」的库，落地页就是那一份数据，
  但如果读完之后又落库了，**再弹一次**数字就变了 —— 以最后一次为准。
- 差很多 ⇒ **停下来**：先回第 1 步，确认自检表本身是对的。

### 第 3 步 · GitHub 上：提交前预览里的 body ↔ 落地页

**你做什么**：在落地页点「去 GitHub 提交」→ 看 GitHub 那个新建 issue 页里的内容（**先别点 Submit**）。

**看到什么算对**

- 标题是 `[report] koreader <最新的一天>`。
- body 是一段 JSON，`"source":"koreader"`，`"days"` 里**每一天的分钟数 = 落地页上那一行的分钟数**。
- 注意 body 里的值是**当天累计总量**，不是增量 —— 所以重复提交不会把数字吃掉。
- 落地页上如果多出一行提醒（某天超过单日上限 1440 分钟），那 body 里那天的值会是**夹过的 1440**，
  页面会写清楚 —— 正常读书碰不到这个（一天 1440 分钟就是 24 小时不睡觉了）。

**对不上怎么办**

- body 里的天数比落地页少 ⇒ 那天超过了单日上限被夹了（落地页会提示），或者 JSON 里被浏览器转义了 ——
  看原始 body，别看渲染后的。
- body 里出现了落地页上没有的日子 ⇒ 不该发生，停下来。

### 第 4 步 · 服务端：issue 下的评论 ↔ 落地页算的

**你做什么**：等结算任务跑完（看 cron 日志，或者隔一天回来看），看那条 issue 下面有没有评论。

**看到什么算对**

- 出现一条评论，长这样：

  ```
  已采纳：3 天的量（koreader），该源口径共折算 7 个额度。

  - 2026-11-19：50 分钟
  - 2026-11-20：25 分钟
  - 2026-11-21：45 分钟
  ```

  - 「**M** = 7 个额度」必须**等于**落地页上那个大数字 ✅
    （50 分钟 → 3 个、25 分钟 → 1 个、45 分钟 → 3 个，合计 7）
  - 「**N** = 3 天」必须等于落地页上列了几行 ✅
  - 每一天后面的分钟数必须等于落地页上那一行的分钟数 ✅
- 账本（`data/dex.json` 的 `ledger`）里能看到对应的那一行，形如：

  ```json
  "2026-11-21": { "weread": 1782, "koreader": 45 }
  ```

  也就是 `{"日期": {"koreader": 分钟}}` ✅ —— **微信读书那份也还在**，
  这正说明两个源是**分开记、额度相加**的（不是把 KOReader 的量塞进微信读书那一栏）。

**没看到评论怎么办**

按这个顺序查：

1. **作者身份**：提交 issue 的账号是不是仓库管理员/协作者？不是 ⇒ 服务端跳过（并且不关 issue，
   留给你看）。
2. **结算任务有没有跑**：看 cron 日志里有没有「发现 N 条报告 issue」。
3. **报告没过校验**（cron 日志会写原因，issue 不会被关）：
   - 日期在未来、或者一次带超过 30 天
   - 某天的量超过该源的 `maxPerDay`（1440 分钟）—— 服务端会**整份丢弃**，不部分采纳
   - `days` 里的值不是非负整数
4. `GITHUB_TOKEN` 没配 / 过期 ⇒ 服务端读不到 issue。

## 沙箱里没能验的部分（老实说）

写这份文档的时候**手上没有真机**（没有 Kindle、没有 Android），下面是**只在真机上才能验**的，
你上手时如果碰到不对，先怀疑这几处：

1. **菜单项出现在哪一组**（位置已经对过上游源码：是「工具 → 更多工具」；
   剩下的不确定只是不同 KOReader 版本 / 语言的分组文案不一样）。
2. **e-ink 屏上的二维码够不够大、相机扫不扫得出来**（沙箱里没有 e-ink 也没相机）。
3. **剪贴板复制能不能成**：`Device.input.setClipboardText` 这个 API 我们没能从上游源码里逐条核实到，
   插件用 `pcall` 包住了，失败就当没这回事（那一行提示不会出现）。
4. **真机上 `conn:exec` 返回值的形状**是否和代码里假设的一样（沙箱里是用 Python 的 sqlite3 验的口径）。
5. **同一天跨零点读书**时两边归到哪一天（两边用同一条 SQL，但值得你亲眼看一次）。
6. **服务端 cron 的实际节奏**（文档里说的是「下一个结算周期」，具体多久看你那边 cron 怎么配）。

除此之外的东西 —— SQL 口径、额度折算、线格式、落地页的数字、服务端的校验和记账 ——
都有单元测试盯着，`python3 -B run_tests.py` 一跑就知道。
