# 微信读书 × 宝可梦收集 —— 设计文档

- 版本：v1.0（2026-11-14）
- 状态：设计已获姜来确认，技术可行性已实测
- 项目目录：`/workspace/pokemon-reading-dex/`

## 1. 目标

复刻小红书那个 KOReader 宝可梦插件的玩法，**但跑在微信读书上**：
每天读满一定时长 → 随机获得一只宝可梦 → 收集全国图鉴 → 连续阅读有稀有度加成。

原帖插件（KOReader，墨水屏）：九世代 1025 种，闪光 1/96，阈值自定。

## 2. 已确认的产品决策

| 决策项 | 结论 |
|---|---|
| 阅读场景 | 手机 App + 电脑网页版**两边都读** |
| 形态 | **两个都要**：服务端判定 + 插件展示 |
| 奖励机制 | **纯随机** + **连续天数有加成** |
| 明确不要 | 阅读之外的其他贡献源；未达标的惩罚感 |
| 共读小屋 | **不搭载**（姜来拍板，功能已完善）。仅共用"我读了多少"这一数据源 |
| 达标阈值 | 默认 30 分钟（1800 秒），可配置 |
| 闪光概率 | 基础 1/96，按连读天数提升，100 天保底 |
| 通知 | 需要推微信通知 |
| 仓库 | 新建独立 repo，不碰 Ink Atlas |

## 3. 架构

```
                    ┌─────────────────────────────┐
                    │  微信读书官方 Agent API      │
                    │  i.weread.qq.com/api/agent/  │
                    │  /readdata/detail            │
                    │  (mode=monthly → 按天分桶)    │
                    └──────────┬──────────────────┘
                               │ readTimes[today] = 秒
                               ▼
                    ┌─────────────────────────────┐
                    │  服务端判定器（唯一权威）      │
                    │  · 阈值判定 / 连读 streak      │
                    │  · 抽卡（未收集池 + 闪光概率）   │
                    │  · 写 dex.json + 推送          │
                    └──────────┬──────────────────┘
                               │ commit
                               ▼
        ┌──────────────────────────────────────────────┐
        │  dex.json（公开 repo，只有图鉴状态）           │
        │  {collected:[{id,name,shiny,at}], today:{...}} │
        └──────────┬───────────────────┬───────────────┘
                   │ fetch              │ fetch
                   ▼                   ▼
        ┌─────────────────┐  ┌────────────────────────┐
        │  图鉴页           │  │  油猴脚本（插件）         │
        │  GitHub Pages   │  │  · 阅读页胶囊进度条       │
        │  lilia-shound.  │  │  · 图鉴墙弹窗            │
        │  github.io/     │  │  · 当日开箱卡            │
        │  pokemon-dex/   │  │  · 只读，不抽不写         │
        └─────────────────┘  └────────────────────────┘
```

### 3.1 权威归属（关键约束）

**服务端是唯一权威。只有服务端抽出的宝可梦进图鉴。**

插件**只读、只展示、不抽卡、不写状态**。理由：
- 姜来在手机上读时没有插件；若两端都能抽，同一天会发两次、状态分叉成两份。
- 服务端独占 `GITHUB_TOKEN` 才能写 repo，插件不该持有写权限。
- 插件展示的"今日已读 X 分钟"读自 `dex.json`（服务端回写），**不把微信读书 API Key 放进插件**。

### 3.2 隐私边界

`dex.json` 是公开的（GitHub Pages 需要能 fetch）。其中**只有**：
- 已收集宝可梦的编号 / 中文名 / 是否闪光 / 获得日期
- 当天已读秒数（用于插件进度条）、连读天数、当日是否已发奖

**不包含**：书架、书名、笔记、划线、微信读书 API Key、历史阅读明细。

## 4. 判定口径（已实测）

### 4.1 接口

```
POST https://i.weread.qq.com/api/agent/gateway
Authorization: Bearer ${WEREAD_API_KEY}     # wrk-...  存于 secret
{"api_name":"/readdata/detail","mode":"monthly","skill_version":"1.0.5"}
```

### 4.2 分桶粒度（实测确认）

| mode | 分桶粒度 | 实测 |
|---|---|---|
| `overall` | 按**年** | 9 桶（2018–2026）✅ |
| `annually` | 按**月** | 12 桶 ✅ |
| `monthly` | 按**天** | baseTime 归一到当月 1 号 ✅ |
| `weekly` | 按**天** | baseTime 归一到本周一 ✅ |

### 4.3 已实测的关键事实与坑

| # | 事实 | 影响 |
|---|---|---|
| 1 | **传历史 `baseTime` 一律返回空**（monthly/weekly/annually 全部试过 2026-05/07/09、2025-06、2023–2025，全部 `桶数=0`） | 官方文档说"可传历史时间戳查看该周期数据"—— **实际不支持**。判定只能用**当前周期** |
| 2 | 所有时长字段单位是**秒** | 阈值 30 分钟 = 1800 秒 |
| 3 | `readDays` 服务端规则：**单日满 1 分钟**算有效阅读天 | 佐证服务端确有"当天达标"概念 |
| 4 | `/shelf/sync` 返回顶层 `{mp,albums,archive,books}`，**无 `bookProgress`** | 网传那篇博客的结构已过时。每本书进度在 `books[]` 内，只有 `updateTime`/`readUpdateTime`/`finishReading`，**没有 readingTime** |
| 5 | 她的 2026 年阅读分布：1月806s、3月75s、4月2445s、5月11663s、6月372s、7月28896s、8月58s、9月6124s、**10月0s、11月0s** | 但 `/shelf/sync` 显示 **11月3日打开过《福尔摩斯探案全集》** → **"打开"不等于"计入时长"**，口径需实测 |
| 6 | 回包带 `upgrade_info` 时必须按指引升级 | 官方 skill 已从 1.0.3 升到 1.0.5，已装到 `/workspace/.skills/weread-skills/` |

### 4.4 待实测项（阻塞"第一圈"）

**微信读书的时长在什么场景下会增长？**

- 微信读书 App 读 → 是否计入 `readTimes`？
- 网页版读 → 是否计入？
- 口径可能是"单页停留 ≥5 秒才计，单页封顶 120 秒"（与 KOReader statistics 插件同款规则）

→ 第一圈需要姜来在微信读书实际读 10 分钟，判定器随后验证。

**兜底设计**：若官方时长在 App + 网页版都不增长，则判定源改为**插件本地计时**（照抄 KOReader 规则：单页 ≥5s 计入、单页封顶 120s、页面隐藏不计），服务端退化为"手机端用官方时长补发"，状态以服务端为准、插件只上报时长。

## 5. 抽卡规则

- **池子**：1025 只里**尚未收集**的。集满 1025 = 通关。
- **闪光**：基础 1/96。
- **连读加成**（streak = 连续达标天数，不达标即归零，**无惩罚**）：

| streak | 闪光概率 |
|---|---|
| 1–2 | 1/96 |
| ≥3 | 1/48 |
| ≥7 | 1/32 |
| ≥30 | 1/16 |
| ≥100 | **保底闪光**（当日必出） |

- 每次达标发 **1 只**。
- streak 满 100 天后保底闪光持续生效，直到 streak 断。

**streak 的显示语义（实现时修正）**：
今天还没达标时，streak 显示的是「截至昨天的连续天数」而不是 0。
因为「已经连读 5 天，今天还没读」和「连读 0 天」体感完全不同 —— 后者会让人以为断了。
今天读满就变 6 天。中间断过则停下重数。

## 6. 数据源

### 6.1 宝可梦（42arch/pokemon-dataset-zh，MIT）

```
data/pokemon/0025-皮卡丘.json          1025 个，中文名 + 完整中文资料
data/images/official/                  官方立绘 1320
data/images/home/                      Pokémon Home 造型 3006
data/images/home/*-shiny.png           闪光变体 ★
```

单只可用字段：
`name_zh` / `pokedex_id` / `description`（一句话简介）/
`profile`（外观描述）/`prototype`（设计原型）/`detail`（冷知识）/
`names`（各语言命名由来）/ `forms`（形态·中文属性·分类·特性·身高体重·捕获率）/
`stats`（种族值）/ `type_effectiveness`（相克）/
**`pokedex_entries[].versions[].text`（各代官方中文图鉴描述）★** /
`evolution_chains`（进化链）/ `home_images`（含 shiny 文件名）

### 6.2 图片分发 —— **实测后改为直链，不落盘**

原计划把 3018 张 PNG 落到仓库里。实测被两个问题逼改了方案：

1. 仓库 52MB，`git push` 在沙箱网络下反复断连（`GnuTLS recv error`），推了 4 次才成功
2. GitHub Pages 与插件都在**姜来的浏览器**里跑，那里本来就访问得到 `raw.githubusercontent.com`

**最终方案**：`data/pokedex.json` 里直接存**完整直链**。

| 来源 | URL 模板 | 数量 |
|---|---|---|
| HOME 造型 | `raw.githubusercontent.com/42arch/pokemon-dataset-zh/main/data/images/home/{文件名}` | 2013 只（含闪光变体） |
| PokeAPI 兜底 | `raw.githubusercontent.com/PokeAPI/sprites/master/sprites/pokemon/other/official-artwork/{编号}.png` | 12 只（无 HOME 造型） |

- 仓库因此从 54MB 降到 **1.8MB**，push 秒过
- 中文文件名已 URL 编码，浏览器直接拉
- **正确性已全量校验**：用 GitHub trees API 拉出 42arch 全部 3006 个 home 文件名，
  与 pokedex.json 里的 2026 个 URL 逐一比对 —— **0 个对不上**；12 个 PokeAPI 兜底逐个查 API 确认存在
- 页面与插件都加了 `onerror` 降级：图裂了就淡成轮廓，不留破图

代价：依赖 42arch 仓库不被删。可接受（该仓库 2026-03 仍在更新）。

## 7. 组件

| 模块 | 职责 | 技术 |
|---|---|---|
| `scripts/fetch_pokemon.py` | 下载 42arch 数据 → 抽取精简字段 → 生成 `data/pokedex.json`（立绘存直链） | Python + git sparse checkout |
| `scripts/weread_client.py` | 调微信读书 gateway，封装 readTimes 取数 | Python，仅用标准库 |
| `scripts/award.py` | 判定（阈值 + streak）→ 抽卡 → 更新 `dex.json` → commit → 推送 | Python + git |
| `scripts/check_today.py` | **自检**：打印今天的桶、原始值、时区对齐情况 | Python |
| `site/` | 图鉴页（静态） | 单页 HTML + JSON |
| `plugin/weread-dex.user.js` | 油猴脚本：胶囊进度条 + 图鉴墙 + 开箱卡 | 原生 JS，无依赖 |
| `data/dex.json` | 唯一状态文件 | JSON，公开 |
| `data/pokedex.json` | 1025 只精简资料（含立绘直链） | JSON |
| `scripts/push_notify.py` | 微信推送（pushplus） | Python 标准库 |
| `scripts/deploy.sh` | 推 main + gh-pages，发布图鉴页 | bash |

### 7.1 插件形态

**油猴脚本**（`.user.js`），双击即装，桌面 + 手机浏览器都能用（Tampermonkey 有 App）。理由：分发最省事，且不绑定油猴专有 API，将来转 Chrome MV3 扩展成本低。

三个功能：
1. **胶囊**：微信读书阅读页右上角浮一个小圆角胶囊，显示「已读 24/30 分」进度条（读 `dex.json` 的当日秒数，3 小时粒度）
2. **图鉴墙弹窗**：已收集亮起 + 立绘 + 中文名 + 编号 + 属性，未收集灰色
3. **开箱卡**：当日达标后点击 → 大图立绘 + 中文名 + 官方中文图鉴描述 + 「✦ 闪光」标记

## 8. 错误处理

| 情况 | 处理 |
|---|---|
| API Key 失效 | 网关返回错误 → 判定器跳过本轮并告警，**不发奖**（绝不因取数失败误发） |
| `readTimes` 无今日桶 | 视为今天 0 秒 → 未达标 |
| 时区错位 | `check_today.py` 打印候选 key（UTC 0 点 / CST 0 点）自动取实际存在的那个；实现上以"最大 key ≤ 今日 CST 0 点"为兜底 |
| 抽取时池子为空 | 1025 只集满 → 记录通关状态，不再发奖 |
| 写 repo 失败 | 不更新本地状态，保留 `dex.json` 不动，下轮重试（**幂等**：先判定是否已发过，再写） |
| 插件 fetch 失败 | 图鉴墙显示"连接不上，稍后重试"，不影响阅读 |

**幂等性**：`dex.json` 里记 `lastAwardDate`，同一天不重复发奖。

## 9. 验收标准

1. `check_today.py` 能在她读完书后打印出**今天**的非零秒数（验证第 4.4 节）
2. 手动跑 `award.py` 能抽出一只宝可梦并写入 `dex.json`
3. `dex.json` 出现在 GitHub repo 上，图鉴页能渲染出这一只
4. 油猴脚本在微信读书阅读页显示胶囊 + 能打开图鉴墙 + 能看到开箱卡
5. 连续两天达标 → streak = 2；连读 3 天 → 闪光概率升到 1/48（可用脚本单元测试验证）
6. 图鉴页中文内容全部正确，无乱码、无英文残留（第九代等 PokeAPI 缺中文的部分由 42arch 兜住）

## 10. 明确不做（YAGNI）

- 不做多账号 / 不做云同步
- 不做宠物养成、进化、喂食等养成系统（纯收集）
- 不做未达标惩罚
- 不做阅读之外的贡献源
- 不做微信通知的富文本（先纯文本推送）
- 不动共读小屋
