# 训练家图鉴 S7 · 日常闭环设计文档

> 日期：2026-11-23
> 上游：`docs/superpowers/specs/2026-11-18-pokemon-dex-hub-design.md`（中枢设计）、S1~S6 已上线
> 状态：设计已由姜来拍板（2026-11-23）

## 1. 目标

S1~S6 把「四个源汇进同一个图鉴」做完了，但**日常闭环有三个洞**：

1. **掉宝可梦她不知道** —— 服务端有 `scripts/push_notify.py`，但 `PUSHPLUS_TOKEN` 从没配过，
   每轮结算都打印「未配置，跳过」。她得**主动刷页面**才知道今天掉没掉。
2. **漏记一天永久归零** —— 额度按天 floor、零头不跨天凑。背单词页能补录最近 7 天，
   **番茄钟页和 KOReader 落地页只能交「今天」** ⇒ 忘了记番茄钟，那天就没了。
3. **看不见自己坚持了多少** —— 图鉴页只有「今天」。没有 7 天 / 30 天的量，没有打卡热力图。

S7 补上这三件事。**核心结算一行不改**。

## 2. 已确认的产品决策（姜来拍板）

| 项 | 决定 | 拍板时问的原话 |
|---|---|---|
| 通知通道 | **邮件（Resend）** | 在 pushplus / Server 酱 / Bark / 邮件里选了邮件 |
| 通知时机 | **掉宝可梦 + 连读快断了** | 「掉宝可梦 + 连读快断了」 |
| 补录入口 | **照搬背单词页的「最近 7 天」格子** | 「照搬背单词页的『最近 7 天』格子」 |
| 历史可视化 | **热力图 + 堆叠柱，两个都要** | 「A + B 两个都要」 |

**「连读快断了」的定义**（本 spec 补充明确，姜来未反对）：

- `streak >= 2`（连读只有 1 天时断了无所谓，不打扰）
- 且**今天还没达标**（当天额度 < `perAward`）
- 且**北京时间（Asia/Shanghai）≥ 21:00**（早上一睁眼就催「你今天还没读」是骚扰）
- 且**今天还没发过这类提醒**（一天最多一封）

**时区**：所有「今天」的判定都用 **Asia/Shanghai**（她的本地时间）。
账本、桶 key 本身也已经是北京时间周期起点 ⇒ 一致。

## 3. 三条设计线

### 3.1 邮件通知（Resend）

#### 3.1.1 边界

**新脚本 `scripts/notify.py`**。它在 `award.py` 之后跑，**只读** `data/dex.json`，
**只写** `data/notify_state.json`。结算核心（`dex_core.py` / `award.py` / `sources.py` / `ledger.py`）
**一行不改**。

> ⚠️ 为什么状态不放 `dex.json`：`scripts/dex_core.py` 的 `build_state()` 返回的是一个
> **重新构造的 dict**（只含固定字段），`award.py` 写回时会**冲掉任何没被它显式带上的字段**。
> 所以「发过提醒」这种状态只能放独立文件。

#### 3.1.2 外部依赖

| 变量 | 存哪 | 说明 |
|---|---|---|
| `RESEND_API_KEY` | Mavis secret（不进 git） | Resend 的 API key（`re_` 开头） |
| `RESEND_TO` | Mavis secret（不进 git） | 收件人邮箱 |

发件人用 Resend 的 `onboarding@resend.dev`（只能发到账号本人的邮箱，单人使用完全够）。
以后有自己的域名再换 —— 换的时候只改一个常量。

**没配置 key 时的行为**：静默跳过并打印 `[通知] 未配置 RESEND_API_KEY，跳过`
（跟现在 `push_notify.py` 的行为一致），**绝不影响发奖流程**。
cron 汇报里要如实提到这一句 —— 别让她以为邮件发出去了。

#### 3.1.3 Resend API

```
POST https://api.resend.com/emails
Authorization: Bearer <RESEND_API_KEY>
Content-Type: application/json

{
  "from": "训练家图鉴 <onboarding@resend.dev>",
  "to": ["<RESEND_TO>"],
  "subject": "训练家图鉴 · 收服了 三海地鼠 No.0961",
  "html": "<html>…</html>"
}
```

- 返回 `{"id": "..."}` = 成功；HTTP 4xx/5xx = 失败
- 免费额度 100 封/天、3000 封/月 ⇒ 实际用量约 1~2 封/天，绰绰有余
- 用 **HTML 邮件**（纯文本太干）
- **立绘用公网链接**：`https://lilia-shound.github.io/pokemon-dex/img/<id>.webp`
  （已经在 gh-pages 上，公开可访问 ⇒ 邮件客户端能直接显示，不用上传附件）

#### 3.1.4 两种邮件的内容

**A. 收服邮件**（`collected` 里有还没通知过的条目）

- 主题：一只时 `训练家图鉴 · 收服了 三海地鼠 No.0961`；多只时 `训练家图鉴 · 收服了 2 只宝可梦`
- 正文：
  - 每只一张卡：**立绘**（大图，居中）+ 名字 + `No.0961` + 属性（中文）
  - 闪光的话：金黄色徽章「✨ 闪光」
  - **哪一天收服的**（`date` 字段）—— 补发的要标出来（「11-21 补发」）
  - 「连读 N 天 · 图鉴 X/1028」
  - 按钮：「去看图鉴」→ `https://lilia-shound.github.io/pokemon-dex/`
  - 一行小字：「这轮的投入：微信读书 30 分钟 + 番茄钟 25 分钟」

**B. 连读提醒**（21:00 后、streak ≥ 2、今天未达标）

- 主题：`今天的连读还差 1 个额度`
- 正文：
  - 「你今天还没凑够 2 个额度，**连读 4 天会在今晚归零**」
  - **具体补多少**：按当天的缺口算，给最省事的组合建议
    （例：还差 1 个额度 → 「再读 15 分钟微信读书」或「一轮番茄钟 25 分钟」）
  - 按钮：「去图鉴」
  - 一行小字：「断了也没惩罚，明天照样能重新开始」← **对齐「未达标 = 没有惩罚」的设计**

#### 3.1.5 幂等

`data/notify_state.json`：

```json
{
  "awarded": ["2026-11-21#0471", "2026-11-22#0163"],
  "streak": { "2026-11-23": true }
}
```

- `awarded` = **已通知过的条目集合**，键是 `date#id`（稳定、可重复计算）
- `streak` = 按天记「这天发过连读提醒」

**★ 判定「有没有新收服」不能只看「今天的条目」** ——
`award.py` 会**一次结清所有待发奖日**（升序，最多 3 天），所以「今天」这轮可能收服的是
**前天甚至大前天**补发的宝可梦。⇒ 规则改成：

> **凡是 `collected` 里出现过的、`awarded` 里还没有的条目，都算「新的」** ⇒ 都要通知。

一封邮件里列全（补发常常不止一只），主题写「收服了 2 只宝可梦」。

- 同一条目**只发一次**（靠 `date#id` 去重）
- 判定「今天抽到了」= `collected` 中存在键不在 `awarded` 里的条目
- **先发再记状态**（先写状态后发信 ⇒ 万一发送失败就永久漏发了；先发后记 ⇒ 最坏情况重复发一封，可接受）

#### 3.1.6 邮件正文里的具体数字怎么算

| 位置 | 规则 |
|---|---|
| 缺几个额度 | `perAward - 当天总额度`（当天总额度 = 各启用源按自己的 `per` 折算后 floor 再相加，与「今日额度」面板同口径） |
| 「再读多少」 | 缺口 × 15 分钟（微信读书 1 额度 = 900 秒 = 15 分钟**官方口径**）。⚠️ 官方计数漏计约三成 ⇒ 体感约 ×1.4 ⇒ 文案写「再读 20 分钟」，**不写 15 分钟** |
| 「今天的投入」 | 各源的原始量 + 折算的额度，列全（她能看到是读书还是番茄钟凑的） |
| 连读天数 | `streak`（= 今天达标才 +1；未达标这天结束时归零） |

#### 3.1.6 cron 接入

**不开新任务** —— 现有 cron 是 `17 */3 * * *`，每天有一轮落在 **21:17**（Asia/Shanghai），
正好是「晚上 9 点还没达标」的时刻。

cron 提示词加一步（跑完 `award.py` 之后）：

```
python3 scripts/notify.py
```

输出含 `[通知] 已发送` / `[通知] 跳过` / `[通知] 未配置`，如实汇报即可。

> ⚠️ cron 提示词是**口径的权威副本**（见中枢设计 §12）—— 改它必须和本 spec 一起改。

### 3.2 补录（番茄钟 + KOReader）

#### 3.2.1 边界

**服务端零改动。** GitHub Issue 投递箱本来就支持：

- 一次报告最多 30 天（`MAX_REPORT_DAYS`）
- 同源同一天取 max ⇒ 重复投递幂等

要做的只是**页面上的「选日期」入口**。

#### 3.2.2 照搬背单词页

`site/words/app.js` 已经把这套跑通了，照抄它的模式：

| 常量 | 值 | 含义 |
|---|---|---|
| `WINDOW_DAYS` | 7 | 页面上显示最近几天（她能在那一排里核对） |
| `MAX_REPORT_DAYS` | 30 | 本地存储窗口（与服务端一次最多收的天数对齐） |

交互：

1. 页面顶部一排「最近 7 天」的日期格子（今天在左）
2. 点某一天 ⇒ 弹出/展开一个输入框，填那天的分钟数
3. 已填过的天数显示数字
4. 填完点「同步到图鉴」⇒ 一次性把最近 30 天里有数的天都投出去
5. 投递成功后给出确认（跟现在的「同步到图鉴」按钮一致）

#### 3.2.3 番茄钟页

**好消息**：番茄钟页本来就在存逐日数据（`S().days = { 'YYYY-MM-DD': {minutes, poms} }`），
还自带一个「近 7 天」柱状图 ⇒ 补录**基本只是加 UI**，存储和投递格式都已支持多天。

要加的：日期格子 + 点某天填数 + 投递时带上那天。

#### 3.2.4 KOReader 落地页

同样加日期格子 + 填那天的分钟数。落地页现在的输入是「今天读了多久」，
改成可以选日期即可。

> ⚠️ KOReader 的分钟数是**从设备端读出来的**，补录是手填 —— 两者口径相同（整分钟、向下取整），
> 但补录的数字没有设备端的时间戳可查，对账时以设备端为准。

### 3.3 历史（热力图 + 堆叠柱）

#### 3.3.1 为什么不用现成的 ledger

`data/dex.json` 的 `ledger` 是**结算用**的。往里回填历史会有副作用：

- `award.py` 的 `pending_days()` 会把「账本里有量、但还没发过奖」的日子当成**待补发日**
- 她 11-01~11-13 每天读了 30 分钟 ⇒ 回填 = 一次性补发 **13 只**宝可梦
- 这不是 bug，是「账本 = 已结算量」这个语义的必然结果

⇒ **历史单独存**，只看不结算。

#### 3.3.2 `data/history.json`

```json
{
  "version": 1,
  "updatedAt": "2026-11-23T08:00:00Z",
  "days": {
    "2026-11-01": { "weread": 1782 },
    "2026-11-21": { "weread": 1245, "pom": 25 }
  }
}
```

- **保留 30 天**（与 `ledgerDays` 对齐）
- **纯展示**：任何结算逻辑都不读它 ⇒ 回填历史**不会**触发补发
- 部署时由 `scripts/deploy.sh` 同步到 `site/history.json`

#### 3.3.3 数据来源

| 源 | 从哪来 | 说明 |
|---|---|---|
| 微信读书 | **月桶回填** | `/readdata/detail` 的 monthly 分桶能给出本月每一天的秒数 ⇒ 一次回填本月全部 |
| 番茄钟 / KOReader / 背单词 | 从 `ledger` 抄 | 推源的历史本来就在账本里 |

写入方：**新脚本 `scripts/history.py`**（cron 每轮跑一次，也可以手动跑）。
它**只写** `data/history.json`，**不碰** `data/dex.json` ⇒ 结算零影响。

#### 3.3.4 图鉴页长什么样

「今日额度」面板**下面**加一块「最近 30 天」：

- **左边：日历热力图** —— 6 列 × 5 行（正好 30 天），每格一天。
  **颜色 = 当天微信读书的秒数**，分档（跟着「额度」刻度走，读者不用背数字）：

  | 档 | 当天微信读书秒数 | 含义 |
  |---|---|---|
  | 空白 | 0 | 那天没读 |
  | 最浅 | 1 ~ 899 | 读了，但不够 1 个额度 |
  | 浅 | 900 ~ 1799 | 够 1 个额度 |
  | 深 | 1800 ~ 2699 | 够 2 个额度（达标线） |
  | 最深 | ≥ 2700 | 超额 |

  图例：少 → 多。
- **右边：四色堆叠柱** —— 每天一根，四个源堆叠。
  ★ **Y 轴 = 当天的额度**（不是分钟！）—— 每个源按自己的 `per` 折算后 floor 再相加，
  **与顶部「今日额度」面板完全同一个口径**，不需要任何拍脑袋的单位换算。
  图例里标出每源的换算：「微信读书 1 额度 = 15 分钟」「番茄钟 1 额度 = 25 分钟」
  「KOReader 1 额度 = 15 分钟」「背单词 1 额度 = 100 个」。
  悬停/点开显示那天的**原始量**。

  > ⚠️ 示意图 `site-check/mock-B.png` 用的是「分钟」轴 —— 那是示意，**正式版改成额度轴**。
  > 理由：背单词 100 个、番茄钟 25 分钟、微信读书 15 分钟，真实耗时差着好几倍，
  > 硬折成同一根柱子的分钟数就是拍脑袋；折成额度则是这个游戏自己的单位，天然一致。

配色沿用站点 CSS 变量：`--bg #f6f1e7` / `--card #fffdf8` / `--ink #2f2823` /
`--dim #9a8d80` / `--line #e9e0d0` / `--accent #c8623a`。
堆叠柱四色：砖橘 `#c8623a`（微信读书）/ 浅橘 `#e2a06a`（番茄钟）/
灰绿 `#7f9a8e`（KOReader）/ 金 `#c9a227`（背单词）。

> 示意图已画好存档：`site-check/mock-A.png`（热力图）、`mock-B.png`（堆叠柱）、`mock-C.png`（累计曲线，未采用）。

## 4. 数据流

```
cron (17 */3 * *, Asia/Shanghai)
  ├─ 1. scripts/collect_reports.py      收 Issue 投递箱
  ├─ 2. scripts/check_today.py           看今天的量
  ├─ 3. scripts/award.py                 判定 + 抽卡        ← 结算核心，不改
  ├─ 4. scripts/notify.py      ★新增     发邮件
  │      ├─ 读 data/dex.json（collected / streak / today）
  │      ├─ 读+写 data/notify_state.json（幂等标记）
  │      └─ Resend API
  ├─ 5. scripts/history.py     ★新增     回填 data/history.json
  └─ 6. scripts/deploy.sh                部署（同步 site/history.json）
```

## 5. 错误处理

| 情况 | 行为 |
|---|---|
| 没配 `RESEND_API_KEY` | 打印 `[通知] 未配置…`，**不报错、不影响发奖** |
| Resend 返回 4xx/5xx | 打印 `[通知] 失败: <msg>`，**不抛异常**（cron 不能因为发信失败就中断） |
| 网络超时 | 同上，`urllib` 超时 20 秒 |
| `data/notify_state.json` 损坏 | 当空字典处理，重新记 |
| `data/history.json` 损坏 | 重建（从账本 + 月桶） |
| 月桶取数失败 | history 里微信读书那段留空，**不影响当天结算** |

**原则**：通知和历史都是**旁路**，任何失败都不能挡住发奖。

## 6. 测试策略

沿用现有规矩：标准库 only、`tests/test_*.py`、类名 `XxxTest`、方法名 `test_xxx`、中文注释。

| 测试文件 | 覆盖 |
|---|---|
| `tests/test_notify.py` | 触发判定（收服 / 连读快断 / 都不触发）、幂等（同一天不重复发）、时间窗（21:00 前不发）、streak=1 不发、没配 key 静默跳过、Resend 错误不抛 |
| `tests/test_history.py` | 月桶回填、保留 30 天、**回填不影响发奖判定**（回归：`pending_days` 不因 history 变化）、损坏文件重建 |
| `tests/test_pomodoro_backfill.py` | 番茄钟页选日期填数、投递体带多天 |
| `tests/test_koreader_backfill.py` | KOReader 落地页选日期填数、投递体带多天 |
| `tests/test_dex_page_s7.py` | 图鉴页历史块渲染（热力图格数 = 30、柱子四色）、history.json 拉不到时的降级 |
| `tests/test_backfill_pages.py` | 两个子页仍满足「只许发一个网络请求」 |

**关键回归断言**：`history.json` 写进去之后，`award.py` 的 `pending_days()` 返回值**必须不变**
—— 这是 3.3.1 那个陷阱的守门测试。

## 7. 交付拆成三次提交

一次提交只做一件事：

1. `feat: 邮件通知（Resend）` —— `scripts/notify.py` + `data/notify_state.json` + cron 提示词 + 文档
2. `feat: 番茄钟与 KOReader 支持补录最近 7 天` —— 两个页面的日期格子 + 测试
3. `feat: 图鉴页加最近 30 天历史（热力图 + 堆叠柱）` —— `scripts/history.py` + `data/history.json` + 前端 + 测试

外加一条：**部署**（`scripts/deploy.sh` 要同步 `site/history.json`）。

## 8. 不做什么（YAGNI）

- **不开第二条 cron** —— 现有 `17 */3 * * *` 的 21:17 那轮就够
- **不做域名邮箱** —— `onboarding@resend.dev` 先用着
- **不做历史导出 / 分享图 / 进化演出** —— 属于「更有意思」那一块，等 S7 落地后再谈
- **不动 `perAward`、不动任何 `per`** —— 背单词口径（10 还是 100）等姜来拍板
- **不做「读完一本书 → 特殊奖励」** —— 想法在 `notes/01-research.md` 里记着，不在这轮
- **不把 history 塞进 `dex.json`** —— `build_state()` 会冲掉未声明的字段
