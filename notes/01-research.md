## 二、核心问题：微信读书上拿不到阅读时长怎么办？

结论：**拿得到，而且有官方接口**。

微信读书 2026 年开放了 Agent API Gateway：

```
POST https://i.weread.qq.com/api/agent/gateway
Authorization: Bearer wrk-xxxxxxxx
{"api_name": "/readdata/detail", "mode": "monthly", "skill_version": "1.0.x"}
```

API Key 获取路径（姜来本地操作）：
- 微信读书 App → 设置 → 微信读书 Skill → 复制 Key
- 或网页端 `https://weread.qq.com/r/weread-skills` 登录后复制
- 格式 `wrk-xxx`，绑定用户身份 vid

### `/readdata/detail` 返回的关键字段

| 字段 | 含义 | 对本项目的价值 |
|---|---|---|
| `readTimes` | 分桶时长，**weekly/monthly 按天分桶**，key=当天起始时间戳，value=秒 | ★ 直接拿「今天读了多少秒」 |
| `totalReadTime` | 周期总时长（秒） | 校验用 |
| `readDays` | 有效阅读天数，**服务端规则：单日满 1 分钟** | 佐证服务端有「当天达标」概念 |
| `dailyReadTimes` | 年度模式下的按天明细 | 备用 |
| `readLongest[]` | 读得最多的书 + 时长 | 可做「读完一本 → 特殊奖励」 |

**注意**：所有时长字段单位是**秒**，文档明确警告不要当分钟/小时用。

判定逻辑因此可以做到：调用 `mode=monthly` → 取 `readTimes` 里今天那个桶 → 秒数 ≥ 阈值 → 达标。

## 七、实测结论（2026-11-14 全部真实验证过）

### 7.1 微信读书接口

| 验证项 | 结果 |
|---|---|
| API Key 有效性 | ✅ 有效，账号 2018–2026 读过 42 本、读完 9 本、161 个有效阅读天、总时长 215 小时 |
| 分桶粒度 | ✅ overall 按年（9 桶）、annually 按月（12 桶）、monthly/weekly 按天 |
| 桶 key 时区 | ✅ **就是北京时间周期起点**（用 monthly 的 baseTime 与 annually 的月桶反推验证，全部精确落在自然周期边界） |
| 时长单位 | ✅ 秒 |
| `readDays` 口径 | ✅ 服务端规则：单日满 1 分钟算有效阅读天 |
| **历史 baseTime** | ❌ **完全不支持**。传 2026-05/07/09、2025-06、2023–2025 全部返回空。官方文档写"可传历史时间戳查看该周期数据"是错的 |
| `/shelf/sync` 结构 | ✅ 顶层 `{mp, albums, archive, books}`，**没有 `bookProgress`**（网传那篇博客的结构已过时）。每本书只有 `updateTime`/`readUpdateTime`/`finishReading`，**没有 readingTime** |
| `upgrade_info` | ⚠️ 回带该字段时官方要求立即升级，已从 1.0.3 升到 1.0.5，装在 `/workspace/.skills/weread-skills/` |

### 7.2 她的实际阅读分布（为什么这个项目需要实测）

`mode=annually`（2026 年）返回的月桶：

```
1月 806s   2月 0    3月 75s    4月 2445s   5月 11663s  6月 372s
7月 28896s 8月 58s  9月 6124s  10月 0      11月 0
```

而 `/shelf/sync` 显示她 **11 月 3 日还打开过《福尔摩斯探案全集》**（updateTime = 2026-11-03）。

→ **"打开"和"计入时长"是两回事**。她最近确实在用微信读书，但官方统计口径没算进去。
原因待实测：可能是「单页停留需 ≥5 秒、单页封顶 120 秒」这类规则（与 KOReader statistics 插件同款），
也可能 App 端与网页端口径不同。

**这是唯一还没钉死的环节**，需要她真读一段才能验证。

### 7.3 宝可梦数据

| 验证项 | 结果 |
|---|---|
| 中文名 | ✅ 1025/1025 |
| 中文图鉴文案 | ✅ 1025/1025（1009 来自官方图鉴，16 只用外观描述兜底；第九代 120/120 全有） |
| 中文属性 | ✅ 1025/1025 |
| 立绘直链正确性 | ✅ **全量校验**：用 GitHub trees API 取 42arch 全部 3006 个 home 文件名，与 pokedex.json 里 2026 个 URL 逐一比对，**0 个对不上**；12 个 PokeAPI 兜底逐个查 API 确认存在 |
| 进化链 | ✅ 拉平后存数组（如 波波 → 比比鸟 → 大比鸟） |

### 7.4 踩掉的坑

1. **`git push` 传 52MB 反复断连**（`GnuTLS recv error` ×4）→ 改成立绘直链不落盘，仓库 54MB → 1.8MB
2. **`git subtree push` 把 token 明文打印到输出** → 改用 `GIT_ASKPASS`
3. **闪光记录被覆盖**：同一只收集多次时 `Map` 后者覆盖前者，闪光版被普通版盖掉 → 改为保留闪光那次
4. **开箱卡开错宝可梦**：取 `collected` 数组最后一条而不是"今天那条" → 改为按日期找
5. **stash 式字符串 patch 容易半途失败** → 改用整文件重写
6. **沙箱网络抖动**：GitHub、jsdelivr、git clone 都可能中途断，需要重试

## 八、第一圈实测（2026-11-14 14:15–14:45，姜来真读了一段）

### 8.1 结论：**机制成立**

她在微信读书读了一段后，接口立刻出现今日桶：

```
2026-11-09 Mon    0 秒
2026-11-10 Tue    0 秒
2026-11-11 Wed    0 秒
2026-11-12 Thu    0 秒
2026-11-13 Fri    0 秒
2026-11-14 Sat  779 秒  ← 她今天读的
```

- ✅ **weekly 与 monthly 都按天分桶**，桶 key 精确对应北京时间每一天 —— 分桶机制与时区**全部确认**
- ✅ 之前 10 月/11 月全是 0，是因为她真的没读；不是口径问题
- ✅ 服务端判定 → 抽卡 → 写 dex.json → 图鉴页/插件展示，整条链路跑通

### 8.2 ★ 发现两个真问题

**① 时长是延迟上报的，而且会持续回补**

每隔约 1 分钟查一次：

```
779 → 838 → 897 → 957 → 1016 → 1076 秒
```

每分钟涨约 60 秒。这意味着：
- 当天读满的数据，**可能到次日凌晨才到**（那时"今天"的桶已经翻页）
- 原实现只看今天 → **会漏发，那只宝可梦永远发不出来**

→ 已实现**补发机制**：判定时扫当前周期内所有「达标但还没发奖」的日期，取最早那天补发。
   幂等改为**按日期判重**（同一日期只发一次）。跨周/跨月边界用 `monthly + weekly` 取并集覆盖。

**② 官方计数漏计约三成**

她实际读了约 25 分钟（14:15 前开始 → 14:38 说读完），官方当时只记了 17 分钟。

→ 达标线按**官方口径**算，体感成本要乘 1.3。
→ 默认阈值从 30 分钟下调到 **15 分钟（官方 900 秒）**，体感约 20~22 分钟。
→ 阈值可用 `DEX_THRESHOLD` 环境变量随时调。

### 8.3 第一只宝可梦

**迭失棺（No.0563）**，非闪光，连读 1 天，图鉴 1/1025。

### 8.4 其他

- 沙箱网络会随机把 2MB 的 `pokedex.json` 拖挂，导致线上页面临时显示"载入中…"。**不是代码 bug**，重试即好。
- `__pycache__` 在 NAS 上时间戳精度不足，改文件后不失效 → 改完代码要清缓存再跑测试，否则会看到"函数不存在"的假报错。
